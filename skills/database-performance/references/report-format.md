# Report Format

Conventions for the two artifacts: evidence references, the Markdown sections and their
contents, the finding block, text diagrams, and the HTML rules and skeleton. Markdown is the
source of truth; the HTML presents the same claims.

All diagrams are plain text in Markdown and HTML/CSS in HTML. No Mermaid, no SVG, no images, no
diagram files.

## Contents

1. Evidence references and labels
2. Markdown sections
3. Finding block
4. Text diagrams
5. HTML rules
6. HTML skeleton

## 1. Evidence references and labels

```text
path/to/file.ext:START-END Symbol     when you read those exact lines
path/to/file.ext Symbol               otherwise
```

- Paths are relative to the analyzed repository root, with forward slashes.
- Symbols: Go `Type.Method` or `Func`; Java, Kotlin, C# `Class#method`; JS/TS `Class.method` or
  `functionName`; Python `module.function`; Ruby `Class#method`; SQL
  `migrations/004_invoices.sql invoices_account_id_idx`; config `config/db.yaml pool.max`.
- Take line numbers only from what you read. Never estimate them.
- Labels are spelled out in upper case: `CONFIRMED (STATIC)`, `CONFIRMED (RUNTIME)`,
  `CONFIRMED (MEASURED)`, `INFERRED` (with "because ..."), `UNKNOWN` (with "resolve by ...").
- Severity is `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, or `OBSERVATION`, followed by its qualifier:
  `static risk`, `runtime-observed`, or `measured`. Priority is `IMMEDIATE INVESTIGATION`,
  `INVESTIGATE`, `MONITOR`, or `OBSERVATION`.

## 2. Markdown sections

Title: `# Database Performance Analysis: <scope>`. Keep this order. Sections marked *required*
always appear. Include the others only when the scope contains what they analyze, and list the
omitted ones in Scope with the reason (for example "Cache Interaction: no cache client in this
repository"). Number the included sections consecutively.

| Section | Contents |
|---|---|
| 1. Scope *(required)* | Metadata block: repository, commit (short SHA or "uncommitted"), analysis date, engines, `Generated by MDW database-performance`. The question asked. What was analyzed (entry points, jobs, tables) and what was not, with why. Evidence available: "static only" or the list of runtime evidence. Query call sites found vs analyzed, and the selection rule. Counts of findings by severity and of `CONFIRMED`/`INFERRED`/`UNKNOWN` items. **Key findings**: 3 to 7 bullets, highest priority first. Omitted sections with reasons |
| 2. Database Architecture *(required)* | `Component \| Value \| Evidence \| Label` for engine, version, driver, ORM/query builder with resolved versions, migration tool, pool library, poolers/proxies, replicas, caches. A text diagram of deployables, pools, and databases. Documentation drift about the database |
| 3. Query Inventory *(required)* | `# \| Query \| Op \| Tables \| Location \| Entry point \| Frequency \| Cost driver \| Tx \| Notes \| Label`. For large repositories, the analyzed subset, plus counts of the rest |
| 4. Performance Findings *(required)* | Summary table `ID \| Finding \| Severity \| Priority \| Confidence \| Location`, sorted by priority then severity. Then one finding block per finding (section 3 of this reference), in the same order. If there are none, say what was checked |
| 5. Query Analysis | Per important query: SQL in a `sql` block (label the text: literal, builder, or ORM-inferred), how it is built (dynamic filters, sort, bounds), its execution path, cost driver, the patterns it matches, and plan status: "Execution plan not available. Run `<engine command>` to validate." or the supplied plan |
| 6. Index Analysis | Effective indexes: `Table \| Index \| Columns (order, direction) \| Type / predicate \| Created \| Dropped \| Label`. Query-to-index alignment: `Query \| Access pattern \| Candidate index \| Alignment \| Rule \| Label`. Missing index candidates (CANDIDATE blocks). Potentially redundant indexes. Foreign keys without an index |
| 7. Transaction Analysis | One TX block per transaction on an important path (`transaction-performance.md` section 2), then implicit transactions |
| 8. Concurrency / Locking | Lock inventory lines; hot rows; potential deadlock risks, each with its interleaving; DDL locking in migrations |
| 9. Connection Pool | `Deployable \| Setting \| Value \| Source \| Default if unset \| Label`; the sizing arithmetic with every factor labeled; what holds connections; leaks; timeouts and cancellation |
| 10. Pagination / Batch Operations | Pagination style per list path with bounds; totals; ordering stability; job iteration; batch writes |
| 11. Cache Interaction | One CACHE block per cache (`caching.md` section 1); invalidation gaps; stampede assessment; repeated queries |
| 12. Runtime Evidence *(required)* | Every RUNTIME and MEASURED record with source, scope, environment, window, and method. If none: "None supplied or captured. Every finding is a static risk; severities are provisional." Then which static claims runtime evidence confirmed, contradicted, or left open |
| 13. Validation Plan *(required)* | One V block per significant finding or recommendation (`database-evidence.md` section 9) |
| 14. Recommended Investigations *(required)* | Grouped under `IMMEDIATE INVESTIGATION`, `INVESTIGATE`, `MONITOR`, `OBSERVATION`: finding IDs, the rule that placed each one, and the first concrete step |
| 15. Confirmed / Inferred / Unknown *(required)* | Three lists, one item per line, each with evidence or reasoning. Subsection **Documentation drift**: `Claim \| Source \| What the code does \| Evidence` |
| 16. Open Questions | `Question \| Why it matters \| Where the answer likely lives`. Subsection **Outside scope** for non-database issues noticed on the way, one line each |
| 17. Evidence *(required)* | Grouped by file: file, then symbols (with line ranges if read), then what each proves |

Every table that holds claims has a `Label` column.

## 3. Finding block

Every field is required. A field with nothing to say gets `none` or `UNKNOWN (resolve by
...)`, never an omission.

```md
### F2. N+1: lines loaded once per invoice on the invoice list

| Field | Value |
|---|---|
| Severity | HIGH — static risk |
| Priority | IMMEDIATE INVESTIGATION (HIGH; pattern CONFIRMED; PER_REQUEST path) |
| Confidence | CONFIRMED (STATIC) for the loop and the query; INFERRED for the cost |
| Location | `internal/billing/service.go InvoiceService.ListForAccount` |
| Path | `GET /accounts/{id}/invoices` -> `InvoiceHandler.List` -> `InvoiceService.ListForAccount` -> `LineRepo.ByInvoice` |
| Frequency | PER_REQUEST; the child query is PER_ITEM |
| Statements | 2 + N per request; N = invoices on the page, <= 100 (clamp in `InvoiceHandler.List`, CONFIRMED) |

**Evidence.** `internal/billing/service.go:41-52 InvoiceService.ListForAccount` calls
`LineRepo.ByInvoice(ctx, inv.ID)` inside `for _, inv := range invoices`.
`internal/billing/line_repo.go ByInvoice` runs
`SELECT ... FROM invoice_lines WHERE invoice_id = $1`. The effective schema has no index on
`invoice_lines.invoice_id` (created in `003`, dropped in `009`).

**Behavior.** One statement for the page, one for the total, then one per invoice, each run
sequentially and each filtering `invoice_lines` on an unindexed column.

**Potential impact.** Statement count grows with page size. Each child statement's cost grows
with the size of `invoice_lines` (size UNKNOWN), because no index serves `invoice_id`
(INFERRED; execution plan not available). The two multiply: N lookups, each potentially
reading the table.

**How to verify.** Count statements for one request with page_size 20 and 100 (SQL logging).
Run `EXPLAIN (ANALYZE, BUFFERS)` for the child query on production-like data. See V2.

**Possible improvement.** Load the lines for all invoices on the page with one query
(`WHERE invoice_id = ANY($1)`) and group them in memory, as `InvoiceService.ListWithPayers`
already does for payers. Separately, evaluate an index candidate on
`invoice_lines (invoice_id)` (Index Analysis, CANDIDATE 1).

**Trade-offs.** One larger result set per request held in memory; the index adds write cost to
every line insert.

**Unknowns.** Row counts of `invoice_lines`; request rate of the endpoint.
```

Rules for the fields:

- **Potential impact** names the cost driver and states every dependency on unknown volume or
  traffic as a condition. It contains no time, rate, row count, or percentage unless a
  measurement record supports it.
- **How to verify** is a concrete method with a metric, not "profile it".
- **Possible improvement** is specific to this repository: the table, the columns, the existing
  code that shows the pattern. It describes the change, and may show a short query shape. It is
  not a patch, a migration, or a rewritten function unless the user asked for one.
- **Trade-offs** includes every correctness change the improvement causes.

## 4. Text diagrams

| Notation | Meaning |
|---|---|
| `[Name]` | a runtime participant: deployable, pool, database, cache |
| indented `Symbol()` | an in-process step |
| `->` | executes, calls |
| `x N` | repeated N times (name N) |
| `BEGIN ... COMMIT` | transaction boundary |
| `(?)` | unknown, explained in Open Questions |

Keep a diagram to 80 columns and about 30 lines. Draw one per question: the deployment and pool
picture, the statement tree of one path, or one transaction.

Deployment and pools:

```text
[billing-api]  x 3 replicas (deploy/k8s/api.yaml)       pool max 40 each (DB_POOL_MAX default)
[billing-worker]  x 1 (deploy/k8s/worker.yaml)          pool max 10
        |
        v
[PostgreSQL 15]  max_connections 200 (deploy/rds.tf)
        demand 3 x 40 + 1 x 10 = 130   CONFIRMED arithmetic on in-repo values
```

Statement tree of one path:

```text
GET /accounts/{id}/invoices                          PER_REQUEST
  InvoiceService.ListForAccount()
    -> SELECT invoices ... LIMIT $2 OFFSET $3        1
    -> SELECT count(*) FROM invoices ...             1
    for each invoice (N <= 100):
      -> SELECT ... FROM invoice_lines WHERE invoice_id = $1      N   (no index)
= 2 + N statements
```

## 5. HTML rules

- Same sections, same order, same claims as the Markdown. Section ids: `scope`, `architecture`,
  `query-inventory`, `findings`, `query-analysis`, `index-analysis`, `transactions`, `locking`,
  `connection-pool`, `pagination-batch`, `cache`, `runtime-evidence`, `validation-plan`,
  `investigations`, `confidence`, `open-questions`, `evidence`. Omit the ids of omitted sections.
- One self-contained file with one inline `<style>`. No `<link>`, no `<script src>`, no web
  fonts, no CDN, no `<img>`, `<svg>`, or `<canvas>`, no framework, no build step. It opens from
  disk and is fully readable with JavaScript disabled; use `<details>` for collapsible content.
- Findings are cards (`article.finding`) showing: title, severity badge and qualifier,
  confidence badge and basis, priority badge, then Location, Path, Frequency, Statements,
  Evidence, Behavior, **Why it matters** (the Potential impact field), How to verify, Possible
  improvement, Trade-offs, Unknowns.
- SQL goes in query blocks (`figure.query` with a caption naming the location and path). Text
  diagrams go in `pre.diagram`. Evidence lists use `ul.evidence`.
- Badges: `span.sev.critical|high|medium|low|observation`, `span.label.confirmed|inferred|unknown`,
  `span.basis` (`STATIC`, `RUNTIME`, `MEASURED`), `span.prio`.
- Escape `<`, `>`, and `&` in SQL, code, diagrams, and table cells.
